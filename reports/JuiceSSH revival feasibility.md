# Revive JuiceSSH Workflows Through Independent Engineering

**A renamed Android successor is technically feasible, but the supplied artifacts are research inputs, not a licensed, buildable JuiceSSH source tree.** The strongest current route is an independently implemented, local-first client that preserves familiar workflows using original UI expression and properly licensed components; a source-based continuation remains conditional on an adequate written grant. Static analysis identifies the original application's architecture and local Pro checks, while OfflineProFix merely overrides several of those checks and cannot recreate cloud authentication or missing services. Historical research recovers a useful public SDK and plugin ecosystem, but neither complete plugin coverage nor compatibility with a renamed host is established. Evidence supports prolonged release inactivity and reported purchase failures, not a declaration that rights expired or every backend is dead. **The research repository is prepared; a successor Android app, app build and runtime tests have not been done, and implementation awaits plan approval.** Findings below synthesize the supplied research dated 18 October 2026, with no earlier report assumed. ([Artifact analysis](../research_notes/JuiceSSH%20revival%20feasibility/artifact-analysis.md), [Historical research](../research_notes/JuiceSSH%20revival%20feasibility/history-and-plugins.md), [Permission research](../research_notes/JuiceSSH%20revival%20feasibility/licensing-and-permission.md))

## Pro unlocks local gates while cloud features need independent services

Pro functionality is embedded in the main APK rather than supplied as a separate client implementation. The inspected entitlement predicate validates a User signature, filters matching product purchases, sorts them by purchase time and accepts the newest matching state 0. The User signature covers session/user and purchase information; a separate method reports remaining session lifetime, and acquisition logic handles cached users, expiry and refresh. Google sign-in and purchase submission are distinct from these local gates. Representative call sites gate forwarding, sharing, shortcuts, some terminal/identity UI, CloudSync and EC2 behavior; this is a partial audited map, not a proof that every paid branch has been enumerated. ([Entitlement and call-site analysis](../research_notes/JuiceSSH%20revival%20feasibility/artifact-analysis.md#2-what-does-offlineprofix-really-change-and-what-rights-accompany-it))

OfflineProFix targets five methods: `oi0.d(Object)` and `pi0.m(Context)` become successful Pro checks, `User.H()` becomes successful signature validation, `User.w()` returns a constant remaining duration, and `pi0.j(Context,p)` calls back with a cached or newly constructed User. The default duration is ten years, configurable within 1–100; it does not persist a real future expiry timestamp. Refresh behavior can still occur without the acquisition override, and a blank fallback User does not contain a valid remote session or recovered purchases. Callback timing changes to synchronous execution, hook failures can be partial, and preference readability across processes remains untested. The module's stated legitimate-purchaser purpose is not enforced by an ownership check. Its AGPL-3.0-or-later statement covers the module, not JuiceSSH. ([Hook analysis and source references](../research_notes/JuiceSSH%20revival%20feasibility/artifact-analysis.md#2-what-does-offlineprofix-really-change-and-what-rights-accompany-it), [Module project](https://github.com/li-yifei/JuiceSSHOfflineProFix))

The historical Pro promise comprises forwarding, EC2 integration, multi-device sync, automatic encrypted backup, a connection/group widget, team sharing, snippets and inactivity locking. The first-party archived feature page specifically names **local, remote and dynamic SOCKS forwarding**, browser launch after tunnel setup, commands/scripts and automatic execution on connection, and AES-256 CloudSync/TeamShare. Home-screen shortcuts additionally appear in the artifact's gated call sites, even though they are not a separate category in the recovered store text. Historical labels are requirements evidence rather than runtime verification; Tasker was separately distributed, themes cannot all be classified as Pro-only from a flattened comparison table, and SFTP API names do not establish a shipped file-browser product. ([Official store specification](https://github.com/Sonelli/juicessh-translations/blob/master/en_US/STORE-LISTING), [Archived first-party features](https://web.archive.org/web/20240318221739id_/https://juicessh.com/partials/features), [Feature distinctions](../research_notes/JuiceSSH%20revival%20feasibility/history-and-plugins.md#3-what-exactly-did-historical-pro-include), [Implementation matrix](../docs/FEATURE_MATRIX.md))

**AES-256 is not a sufficient new security specification.** The inspected legacy field helper uses AES-256-CBC/PKCS5Padding with PBKDF2-HMAC-SHA1 at 1,000 iterations, an eight-byte salt, random IV and three Base64 fields separated by `#`, without a MAC/tag in that helper. SQLite itself was not shown to be fully encrypted. CloudSync wraps selected record types, optionally includes identities, and leaves some relationship/team metadata outside the per-record encrypted wrapper. Those observations neither establish a complete vulnerability chain nor justify calling the entire historical system zero-knowledge. A successor should use a new versioned authenticated-encryption design and retain any legacy decoder only as a narrowly scoped importer. ([Storage and cryptography analysis](../research_notes/JuiceSSH%20revival%20feasibility/artifact-analysis.md#3-what-architecture-is-recoverable-and-what-should-a-renamed-successor-plan-for))

The APK contains HTTPS routes at `api.sonelli.com` for authentication, devices, cloud sync, plugins, purchases, users and logout, with session cookies in inspected authenticated paths. The analyst made no live service requests. Forcing a local success callback cannot create server-accepted credentials, restore unavailable ciphertext, or provide membership and key distribution for TeamShare. EC2 integration also needs its own current AWS API/authentication assessment. Public `gojuice` and `pyjuice` utilities supply backup-format leads, not a replacement server or guaranteed recovery path; `pyjuice` documents incomplete upload/read support. The recommended successor therefore makes local functionality independent of a billing service and treats encrypted backup, multi-device synchronization and team collaboration as distinct later capabilities. ([Service analysis](../research_notes/JuiceSSH%20revival%20feasibility/artifact-analysis.md), [gojuice](https://github.com/Sonelli/gojuice), [pyjuice](https://github.com/markus-li/pyjuice))

## Permission must cover code and expression, not merely maintenance

There is a credible permission route: Sonelli's GitHub organization lists `support@sonelli.com`, and Companies House lists **SONELLI LTD, 07878261, as active**. That formal record does not establish the company's current ownership of every JuiceSSH right. The similarly named dissolved SONELLI SOFTWARE LTD must not be substituted for it. A purchase, inaccessible billing or apparent abandonment does not confer reproduction, modification or distribution rights in the application. SDK/plugin licenses authorize their covered works, not the proprietary host, translations or brand. ([Sonelli contact](https://github.com/Sonelli), [Company record](https://find-and-update.company-information.service.gov.uk/company/07878261), [Directive 2009/24/EC, Arts. 1 and 4–6](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32009L0024), [Actual SDK license](https://raw.githubusercontent.com/Sonelli/juicessh-pluginlibrary/master/LICENSE))

EU law distinguishes lawful observation, necessary interoperability decompilation and necessary error correction. Article 5(3) permits observation during acts a user is entitled to perform; Article 6 requires indispensable interoperability information not readily available, necessary scope and restricted use/disclosure. *SAS Institute* supports reimplementing functionality and formats without treating protected code or manual expression as free to copy. *Top System* recognizes necessary decompilation for error correction under conditions, but does not turn a purchaser's repair into authorization to distribute a derivative client. Whether this specific entitlement failure qualifies has not been established. Czech §66 needs its own analysis, including its specific treatment of technical protection; US §1201 separately regulates circumvention and trafficking and has a conditional interoperability route. These are preliminary jurisdiction-dependent findings, **not legal clearance for this project**. ([Software Directive](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32009L0024), [SAS, C-406/10](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:62010CJ0406), [Top System, C-13/20](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:62020CJ0013), [Czech §66, nonofficial consolidation](https://www.zakonyprolidi.cz/cs/2000-121#p66), [17 USC §1201](https://www.law.cornell.edu/uscode/text/17/1201))

Preserving UX should mean preserving efficient connection management, identity reuse, terminal interaction and automation workflows while designing original screens, icons, copy and layouts. A GUI can carry separate copyright protection even though it is not program expression under the Software Directive; renaming a package or translating decompiled Java into Kotlin does not establish independent creation. Public source without a license is not presumed reusable, and Apache-2.0 does not grant a general trademark license. **The research already includes exposure to decompiled material; no blanket clean-room claim is made.** Record exposure and source provenance, specify behavior without copied implementation, and decide whether a fresh implementation boundary is needed with appropriate advice. ([BSA, C-393/09](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:62009CJ0393), [SAS](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:62010CJ0406), [Apache-2.0 grant and trademark boundary](https://raw.githubusercontent.com/Sonelli/juicessh-pluginlibrary/master/LICENSE), [US false-origin rules](https://www.law.cornell.edu/uscode/text/15/1125))

A practical request should first identify the current owner and authorized signatory, then request an explicit scope for source/build access, reproduction/modification, public source and binary distribution, downstream and commercial rights, versions, territories and duration. Assets, documentation, translations, patents, marks, contributor rights and third-party exclusions need separate treatment. Permission for legitimate-owner repair must distinguish private repair, repair-tool distribution and modified-APK distribution; access to a retired service is not implied. An authorized source release also needs an agreed license compatible with included components, rather than a unilateral license assignment by this workspace. The research includes a complete **unsent permission-email draft** and the registered-office fallback; silence is not consent. ([Permission request and draft](../research_notes/JuiceSSH%20revival%20feasibility/licensing-and-permission.md#draft-permission-email--not-sent), [Rights reserved by EU law](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32009L0024), [17 USC §106](https://www.law.cornell.edu/uscode/text/17/106))

Actual purchase terms/EULA, acquisition evidence, applicable jurisdictions, IP assignments and current rights-holder authority remain missing. The Czech legislative text was obtained through a nonofficial reproduction after the official site returned an application shell; current official consolidation needs checking. UK legal analysis, trademark/patent clearance, US circuit-specific issues and platform-distribution review were not completed. The legal analyst did not inspect the module; the separate artifact analysis establishes its actual AGPL statement and hook behavior, superseding that note's generic tool-audit gap without resolving legal permission. ([Legal scope and gaps](../research_notes/JuiceSSH%20revival%20feasibility/licensing-and-permission.md), [Module-specific analysis](../research_notes/JuiceSSH%20revival%20feasibility/artifact-analysis.md))

## A local-first roadmap turns findings into an approvable successor

The recommended architecture uses a distinct product name, application ID, signing key, provider authority and permission namespace. A Kotlin Android application with an independently designed UI, an SSH-engine adapter, terminal-emulation boundary, session service and local-first persistence is a proposal, not a selected or implemented stack. Engine and terminal candidates must be evaluated from licensed upstream sources for algorithms, host-key trust, keyboard-interactive authentication, forwarding, terminal correctness, Android lifecycle, accessibility, licenses and maintenance. Native choices additionally need contemporary ABI and 16 KiB-page checks. Long-lived session services, notifications, background starts, exported components, storage access and plugin discovery need current Android validation; the analyst's Android documentation fetches failed, so no current Play policy or deadline was verified. ([Proposed architecture](../docs/ARCHITECTURE.md), [Observed platform risks](../research_notes/JuiceSSH%20revival%20feasibility/artifact-analysis.md#modern-android-risks-and-proposed-planning-sequence))

New persistence should separate connections, identities, known hosts, groups, snippets, forwarding rules and execution policy. Credentials require authenticated encryption and explicit key lifecycle decisions; an inactivity screen lock must not be confused with proven cryptographic erasure. Optional AES-256-GCM sync should use a new versioned envelope, documented metadata exposure, key derivation/recovery and conflict/deletion semantics. Team sharing needs an additional membership/revocation/key-distribution design. These are proposed requirements, not an assertion that a new protocol has been secured. A migration reader needs a lawful user-supplied export plus passphrase/account context; a new package cannot ordinarily read the old private database, `allowBackup=false` weakens generic backup assumptions, and plugin-only export is not shown to expose private keys. No fixture has yet demonstrated an import round trip. ([Architecture and migration proposal](../docs/ARCHITECTURE.md), [Observed legacy data constraints](../research_notes/JuiceSSH%20revival%20feasibility/artifact-analysis.md#cited-findings-local-models-and-data-recovery))

The prepared repository now provides a concise entry point, a feature matrix, architecture proposal, approval-gated roadmap and resumable session record. ## Conclusion

The decisive design choice is to preserve the value of JuiceSSH's workflows without preserving dependence on its entitlement service, private package identity or opaque legacy cryptography. That makes an independently branded, offline-capable first release a smaller and more verifiable undertaking than a nominally complete revival whose cloud and plugin guarantees cannot be demonstrated. Permission, if obtained, can expand the reusable inputs; it cannot replace dependency modernization or runtime validation.

The next useful milestone is therefore an approved, evidence-bounded implementation brief with a lawful migration fixture and chosen component evaluation criteria. Success should be measured through reliable SSH sessions, faithful workflow outcomes, demonstrable data import and explicit plugin compatibility—not through whether decompiled code can be made to compile.
