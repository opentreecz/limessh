# R-015 — IME, hardware keyboard edge cases, accessibility (TM-08)

## Scope and exit criteria

- **Question**: What IME input path does JuiceSSH use (composing text, commit vs. keystroke), and does TalkBack / accessibility work correctly with the Compose Canvas terminal?
- **Allowed legacy**: `TerminalEmulatorActivity.java` (IME input handling, `onImeCommitText`, keyboard position setting), `TerminalView.java` (onKeyDown, InputConnection).
- **Current LimeSSH**: `TerminalScreen.kt` (soft input path via `OutlinedTextField`), `keyEventToBytes`.
- **Excluded**: extra keys row (R-013 done), selection/copy (R-012), font/scrollback (other tasks).
- **Deliverable**: spec_ready card; implementation I-R-015.

## Input identity

- JADX: `TerminalEmulatorActivity.java`, `TerminalView.java`.
- LimeSSH: `TerminalScreen.kt:221–235` (IME path), `330–342` (hardware key path).

## Findings and evidence

Preliminary (needs JADX read):

| Evidence ID | Kind | Claim | Locator |
|---|---|---|---|
| EV-015-01 | Observed | LimeSSH uses `OutlinedTextField` buffer: user types → presses Send or ImeAction.Send → entire buffer + `\r` sent as block. This is "cooked mode" input, not raw keystroke streaming | `TerminalScreen.kt:230` |
| EV-015-02 | Observed | JuiceSSH had two keyboard pager pages: page 0 = special keys, page 1 = text input `EditText`. Similar cooked-mode approach for soft keyboard, but page 0 allowed per-key sends | `TerminalEmulatorActivity.java:706` |
| EV-015-03 | Unknown | Whether JuiceSSH streamed each composing keystroke to the terminal vs. committing on commit text only | needs JADX read |
| EV-015-04 | Known | LimeSSH Canvas does not implement `AccessibilityDelegate` or semantic nodes for TalkBack | `TerminalScreen.kt` (no `Modifier.semantics`) |
